# NixOS setup

How the NixOS configuration is structured, how its sources are pinned, and how to rebuild, update and upgrade it. Concrete values (versions, revisions, names) live in the code; this file says where.

## Structure

- `nix/system.nix` is the entry point for `nixos-rebuild`. It evaluates `configuration.nix` with the pinned nixpkgs (see below).
- `nix/configuration.nix` is the main configuration. It defines the machine-specific values (see below), imports the modules, and holds the settings that do not belong to a topic.
- `nix/modules/` has one module per topic. The header comment of each module explains what it is for.
  - `desktop/`: exactly one desktop module is imported at a time (currently Hyprland). Switching needs a reboot.
  - `hardware/`: hardware setup shared by all desktops.
  - `home.nix` and `home/`: home-manager, see [STYLE.md](STYLE.md) for what it manages and why.
- `nix/packages/`: custom package derivations.
- `nix/hardware-configuration.nix` is machine-specific and not in the repository. Generate it on a new machine with `nixos-generate-config --show-hardware-config > ~/nix/hardware-configuration.nix`.

## Machine-specific values

These are defined once, at the top of or in `configuration.nix`. Modules must not repeat them:

- the user name: passed to all modules as the `username` argument
- the host name: modules read it as `config.networking.hostName`
- the monitor names: the `dotfiles.monitors` option (declared in `modules/hardware/monitors.nix`); home-manager modules read it as `osConfig.dotfiles.monitors`

## Pinned sources (lon)

All sources are pinned with [lon](https://github.com/nikstur/lon): nixpkgs, nixpkgs-unstable, home-manager, stylix and lanzaboote. Their branches and revisions are in `nix/lon.lock`, the single place to look them up. `nix/lon.nix` is generated by lon; do not edit it.

- **Why:** rebuilds are reproducible, and the releases of nixpkgs, home-manager and stylix, which must match, are visible in one file.
- **The system is built from the pinned nixpkgs** through `nix/system.nix`, the entry point that `nixos-rebuild` supports since NixOS 26.05. `pb-nixos-rebuild-switch` passes it with `--file`. A plain `sudo nixos-rebuild switch` finds it too, through `/etc/nixos/system.nix`, which `configuration.nix` creates and which forwards to `~/nix/system.nix`. `configuration.nix` still warns if the system was built from another nixpkgs, e.g. through another entry point.
- **No channels:** `nix.channel.enable = false`. `NIX_PATH` points `<nixpkgs>` and `<nixpkgs-unstable>` to the pins, so `nix-shell -p ...` uses the same packages as the system (after a new login following a rebuild).
- **Unstable packages** come from the `nixpkgs-unstable` pin, available to modules as the `unstable` argument (e.g. `unstable.hyprland`).
- **Modules of pinned sources** (home-manager, stylix, lanzaboote) are imported in `configuration.nix` only. They cannot be passed to modules via `_module.args`, since `imports` must not depend on module arguments.
- **Frozen sources** (lanzaboote) are skipped by `lon update`.

## Commands

All are defined in `zsh/nix.zsh`.

| Command | What it does |
|---|---|
| `pb-nixos-rebuild-switch` (`nrs`) | build and activate the system from the pinned nixpkgs |
| `pb-nixos-update-pins` | update all non-frozen pins to the newest commit of their branch (`lon update`); review with `config diff nix/lon.lock` |
| `pb-nixos-update` | update the pins, then rebuild |
| `pb-nixos-version` | show the versions of the pinned nixpkgs sources |
| `pb-nixos-show-generations` | list system generations |
| `pb-nixos-garbage-collection` (`ngc`) | delete unreferenced store paths |

After updating the pins and rebuilding successfully, commit `nix/lon.lock`.

## Upgrading to a new NixOS release

1. Read the release notes of the new release (`nixos/doc/manual/release-notes/` in nixpkgs), especially "Backward Incompatibilities".
2. In `nix/lon.lock`, switch the `branch` of nixpkgs (`nixos-YY.MM`), home-manager and stylix (both `release-YY.MM`) to the new release. They must always be on the same release.
3. Run `pb-nixos-update-pins`, then `pb-nixos-rebuild-switch`, and reboot (kernel and drivers change).

**Never change `system.stateVersion` or `home.stateVersion` for an upgrade.** They are not the version you run (that is the pinned nixpkgs), but the release with which the existing data on the machine (databases, data directories, file locations) was set up. Modules use them to keep compatible defaults for that data; raising them changes those defaults without migrating the data. Only change them for a fresh install, or after migrating the affected data by hand as described in the release notes.

## Secure Boot

Secure Boot via lanzaboote is disabled for now (in the Windows dual boot, some games on Windows crashed although both systems reported Secure Boot as active). Its config is kept commented out in `configuration.nix`, together with the steps to enable it again. lanzaboote stays pinned (frozen) in `nix/lon.lock`.

## Testing changes

- The NixOS config cannot be built on the Mac. `nix-instantiate --parse <file>.nix` checks the syntax only.
- Real checks (option names, conflicting definitions) happen on `perry` with `pb-nixos-rebuild-switch`.
- If a rebuild fails or something is wrong after it, the boot menu and `pb-nixos-show-generations` allow going back to a previous generation.

# Why no flakes?

## What flakes were introduced for

Flakes came out of a Nix design proposal around 2019. They address four problems of classic Nix:

1. **Pinning with a lock file.** A `flake.nix` declares its inputs (nixpkgs, home-manager, …), and `flake.lock` records their exact revisions. That's what lon and `lon.lock` do currently.
2. **Pure evaluation.** In a flake, evaluation must not depend on anything outside the declared inputs: no `NIX_PATH`, no `<nixpkgs>`, no environment variables, no absolute paths like `/home/paul/...`. That's stricter than our setup. For example, `lon.nix` reads environment variables, and `/etc/nixos/system.nix` points into the home folder. Purity also lets Nix cache evaluation results.
3. **A standard interface.** Every flake has a fixed set of outputs: `nixosConfigurations`, `packages`, `devShells`, `apps`, `overlays`, … Tools know where to look, which is what makes these work:
   - `nixos-rebuild --flake .#perry`
   - `nix develop` (development shells)
   - `nix run github:owner/repo` (run a program straight from a repository)
4. **Composition and sharing.** Because the interface is standard, one flake can use another as an input without knowing how it's built. That's how most of the ecosystem (home-manager, stylix, Hyprland) is distributed today.

One caveat: flakes are still marked "experimental" in upstream Nix and have to be enabled explicitly, even though they're widely used. I can't search the web in this session, so it's worth checking whether that changed recently.

## What we would gain now

Not much, because the current setup is essentially a "flake without flakes":

| Flake concept | Current setup |
|---|---|
| `inputs` + `flake.lock` | `lon.lock` |
| `nixosConfigurations.perry` as entry point | `system.nix` |
| `nixos-rebuild --flake` | `nixos-rebuild --file` |

The real differences:

- **Purity:** Nix would enforce that nothing leaks in from outside. Nice, but there is no current problem it would solve.
- **Ecosystem fit:** the docs for home-manager, stylix and Hyprland are mostly written for flakes, so examples would apply directly instead of needing translation. That's a mild convenience.
- **`nix develop` and `devShells`:** these would matter if one wanted per-project development environments. But `nix-shell` with direnv and nix-direnv covers that today, and nix-direnv works with both.

## A specific trap in the current setup

A flake inside a git repository only sees the files git tracks, and it treats the repository root as the flake. The dotfiles repo is a bare repository whose work tree is the whole home folder. Nix wouldn't recognize it as a git repo at all and could copy far more than intended into the store.

The fix is to treat `~/nix` as a plain directory flake (`path:/home/paul/nix`), which also keeps the untracked `hardware-configuration.nix` visible. It's solvable, but it's the kind of hurdle that makes flakes more friction than benefit here.

## My assessment

By the rule in [PLANS.md](PLANS.md) ("only with a clear and strong reason"), I don't see one right now. The pinning works, it's reproducible, and the entry point problem is solved. Good triggers to reconsider:

- **A second machine:** several `nixosConfigurations` in one flake that share modules is a strength of flakes.
- **A tool needed that's only available as a flake.**
- **Wanting `nix develop` dev shells** for projects.

If one of those comes up, the migration would be small: the structure of `lon.lock` and `system.nix` maps one-to-one onto `flake.nix` and `flake.lock`.
